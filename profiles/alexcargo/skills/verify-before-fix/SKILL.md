# Verify Before Fix

Stefan's hard rule (2026-07-28): **any hypothesis about WHY something broke must
be confirmed by a FACT (real API call / log line / actual output) BEFORE editing
code.** Do not guess the root cause and start fixing unverified. False hypotheses
build the whole system on sand and break everything downstream.

## The failure pattern (what NOT to do)
- Take a static test failure (e.g. a bare `urllib` POST returning 403) as proof
  "the key / model / endpoint is dead".
- Reason "Hermes works on X → therefore the object's problem is Y" without
  reproducing the object's actual call path.
- Start editing code to "fix" the unverified guess. (This is how Richard's 403
  rabbit-hole happened: 6+ edits based on a urllib 403 that was actually a
  wrong client, not a dead key.)

## The correct pattern
1. State the hypothesis explicitly.
2. Reproduce the component's ACTUAL runtime call (not a stripped-down test) and
   observe the real result.
3. Only after the fact contradicts/confirms — decide the fix.
If "I (Hermes) work fine on X" → X is healthy → the problem is in the TARGET's
code, not its credentials. Reproduce the target's call to prove it.

## Bot / agent self-verification (DO, don't ping the human)
- DO verify a bot by calling its logic directly in the same runtime:
  ```python
  import importlib.util, os
  spec = importlib.util.spec_from_file_location("rb", "path/to/bot.py")
  rb = importlib.util.module_from_spec(spec)
  try: spec.loader.exec_module(rb)
  except SystemExit: pass
  print(rb.llm_chat([{"role":"user","content":"ping"}]))
  ```
  Inspect the answer AND which model/provider answered.
- DON'T ask Stefan to "write to the bot and tell me what it says" — self-verify.
- DON'T call Telegram `getUpdates` manually against a running bot — it 409-conflicts
  with the bot's own long-poll and silently eats its queue (bit Liz & Richard).

## Nous-specific gotcha
Nous (`inference-api.nousresearch.com`) accepts requests ONLY via the OpenAI SDK
client (`_create_openai_client` from `hermes-agent/agent/auxiliary_client.py`),
NOT a bare `urllib` POST. A urllib 403 is NOT proof the key is dead — the SDK
works (Hermes itself uses it). If a bot 403s, switch its `llm_chat` to the SDK
client, don't go hunting for a "broken key".

## After resolving
Record the case in long-term memory: `python memory_v2/add_case.py <slug> "<desc>" "<lesson>"`
(or via the memory-recall skill). Embed the verified root cause, not the guess.

## Telegram-agent diagnosis: blank reply / short-context loss / nonsense-word bursts

When a Telegram bot suddenly sends an empty-cool / off-topic / boilerplate reply or
drops context between neighboring messages, do NOT jump to changing prompts or models
until you have confirmed **two facts in this order**:

1. **Is this message the bot's own prose, or a coded stub/template?**
   - Search the bot's codebase for any substring from the unexpected reply.
   - If it is NOT present, the text was generated by the LLM, not emitted by code.
   - Common stubs to rule out first: `lost the line`, `stub message`, bare `print`
     statements that reach the user, `RICHARD_STUB_MESSAGE`, or a default
     `context too short` response defined somewhere in `run_agent`.

2. **Which model actually answered?**
   - Inspect the bot's fallback chain (e.g. `free_models.json`, env vars like
     `RICHARD_MODEL`).
   - Look at the bot's own log for `model <name> failed: ... trying next`.
   - A different free-tier model can dramatically change tone and quality even when
     the prompt is unchanged.

**Then and only then** decide the fix class:
- Coded stub/early-return → patch the stub/handler, not the prompt.
- True LLM generation → tighten the prompt (one concrete work-related question or
  silence), and only if the model is the issue consider narrowing the fallback
  list to proven-good models.
- Repeated fallbacks between similar-quality models often point to network/proxy
  errors (409/429/502/503) rather than model quality — log first, edit second.

**Anti-pattern:** changing prompts/code because the UI looks wrong, then discovering
the live process never picked up the change. Before retrying, verify the running
process's file path, PID, and command line; stale `.pyc`, multiple `pythonw`
instances, and edits in a temp copy instead of the live file are common causes.
