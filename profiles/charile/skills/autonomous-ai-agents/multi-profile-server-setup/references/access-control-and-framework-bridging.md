# Multi-Profile Access Control, Telegram Token Isolation & Native Framework Bridging

## 1. Telegram RBAC & Ownership Security (Preventing "Set Home Chat" Hijacks)
When deploying bots for team-wide use (e.g. `allow_from: ["*"]`):
- **Hard-bind `home_channel`:** Explicitly set `home_channel.platform: telegram` and `home_channel.chat_id: "<OWNER_TG_ID>"`.
- **Restrict Slash Commands:** Place `<OWNER_TG_ID>` in `allow_admin_from: ["<OWNER_TG_ID>"]` to block non-admin team members from reconfiguring the agent, resetting memory, or invoking `/set` commands.
- **YAML List Syntax Warning:** Ensure `allow_from` and `allow_admin_from` in `config.yaml` are clean native YAML arrays (not stringified JSON arrays like `'["..."]'`), which can trip parser validation and result in `Blocked unauthorized user` log drops.

## 2. GitHub Push Protection & Secret Unblocking
When pushing commits to GitHub repos containing sample tokens or legacy credentials:
- GitHub Secret Scanning rejects pushes with `GH013: Repository rule violations found`.
- Provide the user with the direct unblock URL generated by GitHub (`/security/secret-scanning/unblock-secret/<HASH>`) to whitelist false positives in 1 click.

## 3. Dedicated Agent Frameworks vs Hermes Wrapper
- If an agent is built on an autonomous framework with its own native runner/GitHub Actions harness (such as **Aeon Framework**), do not run it inside a standard `hermes gateway run` systemd unit.
- Deploy the agent directly in its native environment (e.g., GitHub Actions workflows `.github/workflows/messages.yml` and `aeon.yml` with encrypted secrets `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, and LLM gateway keys).

## 4. Fallback Priority with Stealth Models
- Keep bleeding-edge, high-context free models (such as `stealth/ox-alpha` on OpenRouter with 1M context) at Step 1 of `fallback_providers` across all profile `config.yaml` files to absorb upstream provider outages (e.g. Gemini 503 spikes).
